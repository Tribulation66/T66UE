## Dynamic Mob HISM Rendering Regresses Full-Resolution Lightweight FPS

- Severity tag: [Major]
- Status: CLOSED - NO-LAND (2026-05-29). This is no longer a pending item. B.13 was formally closed as a no-land: instanced rendering (HISM and ISM) empirically regressed full-resolution FPS for constantly-moving VAT mobs in UE 5.7, so nothing was landed and the per-mob static-mesh renderer is the chosen, deliberate renderer. Authoritative consolidation: `PerformanceSystem/B13_MobInstancedRendering_Audit.md`. The GPU-driven crowd renderer is the deferred escape hatch, to be revisited only if enemy counts exceed the design ceiling and rendering becomes the measured bottleneck. The entries below are retained as historical evidence.
- What's wrong: The B.13 isolated de-risk pass proved VAT frame animation through per-instance custom data, but every HISM variant regressed full-resolution FPS versus the pre-B.13 lightweight baseline. The best HISM variant (`frame-only material`, sparse custom-data writes) produced `172.64` median FPS, `139.61` 1% low, and `68.98` 0.1% low versus the before baseline `189.65`, `156.16`, and `72.03`. A plain ISM feasibility variant improved over HISM but still only reached `176.42` median FPS.
- B.13 continuation update: additional isolated candidates ruled out the remaining obvious HISM explanations. Unregistering the old per-mob `VisualMesh` crashed in `FPrimitiveSceneInfo::UpdateComponentLastRenderTime`; safe render suppression was stable but still only reached `176.83` median FPS; moving hidden pooled instances from offscreen to origin worsened to `169.16`; and a last-transform cache worsened to `171.53`. UE 5.7 source inspection confirmed that HISM batch transform updates still route through per-instance `UpdateInstanceTransform` and `BuildTreeIfOutdated` for moving instances, so the hierarchy/update path itself is the likely cost center.
- B.13R spatial-cell update: a reviewed spatial-cell HISM continuation moved fine visual movement into per-instance custom data (`Frame`, `OffsetX/Y/Z`) and only updated HISM transforms when crossing coarse cells. Correctness proofs passed (`VisibleVisualMeshesWhileHISM=0`, independent frame values, all-family HISM coverage), and a saturated screenshot showed mobs visible and co-located. Performance still failed: `2000` uu cells regressed to `80.42` median FPS; `500` uu cells reached only `167.21`; disabling HISM shadows/decals reached `177.31`; lazy pooled allocation reached `176.01`; and the best final probe, which also nulled the actor mesh on HISM takeover, reached `179.36` median FPS with strong lows (`157.71` 1% low, `139.87` 0.1% low) but still missed the `189.65` median baseline by `10.30` FPS.
- Why it is closed: The reviewed B.13 scope explicitly targeted HISM/ISM instancing. The de-risk gate did its job and prevented a regressing renderer from being copied into live source. The user decided to close B.13 as a no-land and keep the per-mob static-mesh renderer as the deliberate choice. Pivoting to a different crowd-rendering architecture requires a new reviewed packet and is deferred.
- What a future renderer pass would entail: A new reviewed packet (provisionally "B.13R") designed around the actual bottleneck - dynamic per-frame instance transform updates. The recorded preferred direction is a GPU-driven crowd renderer with manager-owned position/frame data in a buffer or texture read in the vertex shader, bypassing UE component instance transforms. Lower-value alternatives previously noted: partial instancing for non-moving/death states, or lower-frequency transform updates with visual interpolation proof. Revisit only if enemy counts exceed the design ceiling and rendering becomes the measured bottleneck. See `PerformanceSystem/B13_MobInstancedRendering_Audit.md`.
